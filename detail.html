이중화 없는 외부 의존 구조 — 같은 패턴의 장애가 3년째 반복되고 있다

왜 오프라인 발권이 대안이 될 수 없나?

🪑

좌석·예약 동기화 불가

예약 원본이 항공사 중앙 시스템에만 존재. 오프라인 처리 시 중복 배정·초과 판매 발생 위험. 당일 예약 변경·재발권·좌석 변경은 불가.

🛂

출입국·보안 심사 우회 불가

탑승자 사전 확인(APISystem) 등 당국 서버의 실시간 "탑승 가능" 응답 필수. 시스템 우회 시 위법.

🔄

복구 후 데이터 충돌 (CAP 딜레마)

분산 처리 중 같은 좌석 이중 배정·수하물 불일치 발생 가능. 항공 안전 기준상 가용성보다 일관성을 택해야 하므로 오프라인 처리 후 수동 검토 필수.

💼

투자·책임 주체 분리

공용 카운터 통신망(공항↔에어링크 계약)과 발권 시스템(항공사 자체)이 별개. 장애 시 어느 쪽도 전체 백업에 단독 책임이 없는 구조.

반복되는 단일 공급자 의존 장애 이력

일시장애 원인영향 공항·규모교훈
2024년 7월 MS·CrowdStrike 글로벌 IT 대란 인천공항: 에어프레미아·제주·이스타 등 101편 지연, 4편 결항 자체 클라우드 항공사는 무피해 → 백업 여부가 피해 결정
2025년 9월 에어링크 MUSE 시스템 랜섬웨어 공격 히스로·브뤼셀·베를린 — 수기 체크인, 지연·결항 BA는 자체 백업으로 운항 유지. 집중 리스크 대표 사례
2026년 10월 ARINC 통신망 + TravelSky 중첩 장애 인천공항: 38편 지연, 1,200명 대기, 12시간 복구 이중 공급자 의존 + 자동 전환 부재가 피해 극대화
패턴 인식 3건 모두 단일 외부 공급자 시스템 의존 + 자동 페일오버 부재라는 동일한 구조적 취약점에서 비롯됐다. 이는 기술적 개선이 아닌 아키텍처 수준의 문제다.
📖 CAP 정리 심화: 항공 DCS가 일관성을 선택할 수밖에 없는 3가지 이유

분산 시스템은 네트워크 분단(Partition) 발생 시 가용성(Availability)과 일관성(Consistency) 중 하나를 포기해야 한다(CAP 정리). 항공 DCS는 아래 이유로 반드시 일관성을 선택해야 한다.

이유 1

좌석 중복 배정 → 안전·법적 책임

두 카운터가 동시에 같은 좌석을 배정하면 오버부킹이 발생한다. 항공기 무게중심 계산 오류로 이어질 수 있어 안전 문제다.

이유 2

수하물-탑승객 불일치 → 보안 규정

ICAO Annex 17 기준, 탑승하지 않은 승객의 수하물은 반드시 하기해야 한다. 오프라인 처리 중 불일치 발생 시 전 항공편 지연.

이유 3

API 출입국 심사 실시간 의무

한국 출입국관리법상 탑승자 사전확인(API) — 당국 서버의 실시간 "탑승 가능" 응답 없이 탑승 처리 시 위법.

💡 타 산업과의 차이
인터넷 쇼핑몰은 가용성을 선택해 "재고 임시 할당"을 허용한다. 항공은 안전·보안·법규로 인해 이 선택이 불가능하다. 따라서 "오프라인을 더 잘 만드는 것"이 아니라 "오프라인이 필요 없도록 이중화하는 것"이 유일한 해법이다.
3

SPOF + 수동 전환 + 취약한 오프라인 — 공항 IT의 3중 구조 결함

핵심 문제 정의 미션 크리티컬 인프라가 단일 외부 공급자 네트워크/시스템에 단독 의존하면서, 장애 감지–전환–복구를 자동화하지 않아 수동 대응의 처리 한계가 서비스 중단으로 직결된다.

일반화: 3계층 취약 구조

계층 1

단일 장애점 (SPOF)

ARINC·TravelSky 등 단일 외부 시스템에 업무 전체가 묶여 있어, 해당 시스템 장애 = 전체 서비스 중단.

계층 2

자동 전환 부재

장애 감지→백업 전환이 수동. 감지 지연 + 담당자 대응 시간 + 수동 전환 절차로 수시간 공백 발생.

계층 3

오프라인 처리 능력 부족

백업 전환 후에도 로컬에서 처리 가능한 업무 범위가 좁고, 복구 후 데이터 동기화 자동화 없음.

일반화된 문제: 어디서든 반복된다

이 구조는 항공 산업에 국한되지 않는다. 동일한 패턴이 아래 분야에서 반복적으로 나타난다.

공항 체크인 시스템 IoT 엣지 컴퓨팅 금융 결제 게이트웨이 산업용 제어 시스템 (ICS) 스마트 공장 MES 병원 의료 정보 시스템 물류 창고 관리 시스템
일반화된 요구사항 ① 다중 공급자·경로 이중화  |  ② 장애 자동 감지 및 즉각 전환  |  ③ 오프라인 모드 운영 능력  |  ④ 복구 후 자동 동기화 및 충돌 해소

타 산업의 선행 해결 사례

산업문제해결 방식항공에 적용 가능한 시사점
금융 (카드사·은행) 단일 VAN망 장애 시 전국 결제 중단 금융위원회 규정으로 이중 VAN 의무화. 주 망 장애 시 자동 전환(Active-Standby) 규제 의무화 + 자동 전환이 병행될 때 실효성 있음
통신사 기지국 단일 코어망 의존 시 지역 전체 불통 다중 코어망(Primary·Secondary·Tertiary) + 실시간 트래픽 리밸런싱 경로 다중화 + AI 트래픽 분산이 다운타임을 수ms 이내로 제어
클라우드 (AWS·Azure) AZ(가용영역) 장애 시 서비스 중단 Multi-AZ 자동 페일오버. RTO(복구목표시간) <60초 SLA 자동 페일오버 SLA를 계약에 명문화 → 책임 소재 명확화
항공 (일부 선진사) GDS·DCS 장애 시 체크인 중단 British Airways: 자체 DCS 백업 보유 → 2025년 ARINC 랜섬웨어 시 운항 유지 자체 백업 DCS + 로컬 캐시가 핵심. 인천공항 중국 3사에 부재.
공통 교훈 어떤 산업이든 해결 패턴은 동일하다: ① 다중 경로 구성 → ② 자동 감지·전환 → ③ 오프라인 처리 가능 범위 최대화 → ④ 복구 후 자동 병합. 규제 의무화가 선행된 산업(금융·통신)은 이미 해결했고, 항공은 뒤처져 있다.

PureEdge 4단계 작동 원리

1단계

감시 (Monitor)

엣지 노드 상태·에너지·처리 부하·네트워크 지연을 실시간 수집. IoT 디바이스 및 에이전트가 주기적 상태 보고.

2단계

예측 (Predict)

Random Forest 분류기가 수집 데이터를 분석해 장애 발생 가능성 및 최적 경로를 예측. 반응형이 아닌 예방형 전환.

3단계

경로 선택 (Route)

Primary 유지 / Backup(IPFS) 전환 / Offline(Pure Wallet+) 전환 중 최적 결정을 20~30ms 내 자동 실행.

4단계

복구 (Recover)

Primary 라인 복구 감지 시 오프라인 기록 자동 동기화. 충돌 트랜잭션만 예외 처리 큐로 분리.

  • Random Forest 분류기 기반 경량 모델 — 저사양 엣지 디바이스에서도 구동
  • 에너지 레벨·처리 부하·장애 이력을 실시간 수집·분석
  • ML 모델이 잠재 장애를 사전 예측 (반응형이 아닌 예측형)
  • Primary 유지 / Backup 전환 / Offline 전환 3가지 결정을 자동 실행
  • 과거 실패 패턴에서 지속 학습 → 점진적 정확도 향상

연동 제품 생태계

  • Pure Edge — AI 스케줄링 엔진·페일오버 컨트롤러
  • Pure Chain — Backup 경로의 IPFS 기반 분산 원장
  • Pure Wallet+ — Offline 모드 로컬 트랜잭션 처리 경로
  • 3개 제품이 연계하여 Primary→Backup→Offline 3단계 커버
  • 모듈형 구조로 기존 시스템에 최소 변경으로 통합 가능

학습 데이터 (입력 피처)

  • 에너지 레벨 — 각 엣지 노드의 잔여 배터리/전원 상태
  • 처리 부하 — CPU·메모리·네트워크 I/O 실시간 수치
  • 장애 이력 — 과거 페일오버 발생 시점·원인·지속 시간 패턴
  • 네트워크 지연 — Primary↔Backup 간 RTT(Round Trip Time)
  • 트랜잭션 성공률 — 최근 N분 윈도우 내 요청 처리 성공/실패 비율

Random Forest의 장점 단일 결정 트리 대비 과적합 방지, 노이즈에 강건. 경량 모델로 저사양 엣지 디바이스(IoT 센서급)에서도 실시간 추론 가능. Deep Learning 대비 학습 데이터 요구량 적고 설명 가능성(explainability) 높음 — 페일오버 결정 근거를 로그로 확인 가능.
🔗 IPFS + 블록체인 저장 기술 상세
  • IPFS — 중앙 서버 없는 분산 파일 시스템. 데이터 무결성 자동 검증.
  • 변조 불가 — 저장된 체크인 기록은 블록체인 원장에 연결돼 사후 수정·삭제 불가. 분쟁 발생 시 법적 증거력 확보.
  • 네트워크 복구 후 자동 병합 — IPFS 노드가 온라인 복귀 시 P2P 방식으로 메인 네트워크와 자동 동기화. 중앙 동기화 서버 불필요.
  • Pure Chain과의 연동 — Pure Chain이 IPFS 위에서 항공 트랜잭션 전용 원장을 운영. 체크인 기록, 좌석 배정 스냅샷, 수하물 매칭 이력 저장.
  • Pure Wallet+ — 오프라인 상태에서 로컬에 트랜잭션을 서명·저장. 복구 후 Pure Chain에 제출하면 자동 검증·병합.
💡 항공 적용 시 의미
TravelSky 장애 중에도 Pure Wallet+가 승객 체크인 기록을 로컬에 블록체인 서명으로 저장 → 복구 후 TravelSky와 자동 병합. 기존 수기 수속의 "나중에 수동 재입력" 과정이 완전 자동화된다.

페일오버 시간 분산 분석 — 예측 가능성의 중요성

논문 Figure 3 박스플롯에서 드러난 핵심 차이는 단순 평균값이 아닌 분산(variance)이다.

Round Robin / Energy-Aware — 높은 분산 페일오버 시간의 범위(min~max)가 넓다. 최악의 경우 10ms 이상 소요. 서비스 품질이 예측 불가하며, 하드 리얼타임 요건이 있는 시스템에서 SLA 위반 위험.
PureEdge AI — 낮은 분산 + 낮은 중앙값 페일오버 시간이 좁은 범위에 집중. 중앙값도 낮고 이상치(outlier)도 적다. 예측 가능한 성능이 보장 — 항공 체크인처럼 "몇 초 안에 반응이 와야 하는" 시스템에 적합.
CDF(누적 분포 함수) 분석 결과 (논문 Figure 5) PureEdge AI의 CDF 곡선이 다른 두 방식보다 왼쪽(낮은 전환 시간 방향)에 위치. 동일한 전환 시간 임계값(예: 6ms) 기준으로 PureEdge AI의 누적 처리율이 Round Robin·Energy-Aware보다 현저히 높다. 즉 "더 빠르게, 더 자주" 전환을 완료한다.

현재 투자 주체(공항 vs 항공사)가 분리돼 있어 이중화 유인이 낮다. 이번 사고를 계기로 공항공사·항공사·통신망 업체 3자 비용 분담 협약 체결 방안 검토 필요.

🔔

외부 시스템 장애 실시간 통보 의무

이번 사고에서 공항공사가 에어링크로부터 장애 원인을 통보받지 못했다. 해외 통신망 업체의 장애 발생 시 공항공사에 30분 이내 통보를 계약 의무 조항으로 명문화해야 한다.

🌐

IATA/ICAO 표준화 참여

국제항공운송협회(IATA)의 DCS 이중화 가이드라인 제정 논의에 한국 공항공사·항공사가 참여하여 글로벌 기준 형성에 기여. PureEdge 솔루션을 글로벌 레퍼런스로 제시 가능.

도입 리스크 및 대응 방안

리스크발생 가능성영향도대응 방안
기존 ARINC 계약 잠금(Lock-in) 높음 중간 계약 갱신 시 이중화 조항 추가, PureEdge를 ARINC 위 레이어로 구성해 계약 충돌 최소화
AI 오판에 의한 불필요 전환 낮음 중간 전환 임계값 조정 가능. 초기 파일럿 단계에서 사람 확인 병행. 이력 학습으로 오판율 감소
오프라인 처리 범위의 법적 한계 중간 높음 Pure Wallet+의 처리 범위를 법적으로 허용된 범위(기존 예약 체크인)로 한정. API 심사는 별도 채널 유지
항공사 간 시스템 이질성 높음 중간 PureEdge의 모듈형 구조 활용. 항공사별 DCS에 맞는 어댑터 레이어 구현
블록체인 데이터의 항공 당국 인정 중간 높음 IPFS 기록의 법적 증거력 확보를 위해 국토교통부·법무부 사전 협의 필요

PureEdge 향후 발전 방향 (논문 Future Work 기반)

강화학습(RL) 통합

현재 Random Forest(지도학습) → 강화학습 에이전트로 업그레이드. 실시간 환경 변화에 스스로 적응하는 자가 진화 페일오버 시스템 구현.

중기

블록체인 기반 인증 강화

장기

예측형 에너지 관리
